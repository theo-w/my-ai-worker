整体逻辑流程与规则 / LLM 生效时机

数字分身负责目标、规划、反馈处理和重规划；数字员工负责按能力执行任务、报告进度与结果。规则在输入、权限、状态、证据和验收边界生效；LLM 只在明确配置的规划、执行、研究总结或重规划节点调用。

按 capability 选择执行器与工具
权限 / 状态规则搜索 / 模型配置
4. 执行与留痕
输出、来源、尝试次数、事件、心跳
可选 LLM 执行状态机 / 记录
↓

来源去重、字段检查、质量过滤
确定性规则无合格证据则阻断研究任务

任务完成与事实正确分开

数字分身 ↔ 数字员工：双向协作闭环

分身不是简单的任务分发器；员工也不是只返回一段文本的工具。分身管理目标、计划与取舍，员工负责有边界地执行并报告真实状态。以下是目标行为；当前不同执行路径尚未全部统一，不能把设计图当成已完成的端到端能力。

1. 分身接收目标
保存目标、约束、成功标准和风险等级。
输入校验 / 策略规则
2. 分身决定如何组织
先判断单代理是否足够；只有存在明确分工收益时才拆成多个任务。
LLM 可提出计划规则校验计划
3. 员工接收并确认
按能力、身份、权限与任务租约领取工作。
权限 / 能力 / 租约检查
4. 员工执行并持续反馈
提交进度、结果、证据来源或阻塞原因；心跳只代表存活，不代表工作成功。
LLM / 搜索 / 工具按配置调用
5. 分身处理反馈
决定继续、补充输入、重试、改派、合并、取消或重规划。
状态与次数边界可选 LLM 重规划
6. 独立验收
员工不能自己批准自己的结果；失败时记录原因并返回分身决策环节。
验收门槛 / 权限边界
7. 记忆与改进
记录决策、反馈、成本和结果；先生成改进假设，评估与批准后才考虑采用。
当前为观察模式
↺ 未通过、阻塞或目标变化时，返回第 2 或第 5 步；完成后汇报用户。
当前实现边界：任务信箱已支持创建、领取、心跳、进度/结果反馈、等待验收、管理员验证和重试边界；工作台快速运行、项目自主循环和持久化员工信箱目前仍是并存路径。要实现真正持续管理，下一步必须把“分身决策 → 信箱任务 → 员工反馈 → 分身再决策”接成一条受测的运行时闭环。不要把员工心跳当成完成状态，也不要把 LLM 输出当成独立证据。

当前有三条并存的执行路径（不要混为一条）

路径 A · 项目规划与执行

入口：POST /api/autonomous
请求校验目标、任务格式、动作边界先由代码检查。
↓
规划若请求已提供 tasks，则跳过自动规划；否则尝试 LLM 规划，未配置或响应无效时退回确定性计划。
↓
审批门槛发布、预算承诺、对外发布、破坏性操作、法律承诺等受保护动作会先要求审批。
↓
执行器路由研究任务要求真实搜索 provider；其他任务可走 LLM executor；没有任何实时集成时走明确标记的模拟执行。
↓
结果与准确性标记返回任务、来源信任级别与未验证输出数；接口明确不授权基于这些输出直接作事实决策。

路径 C · 工作台快速运行（演示/旧流程）

入口：POST /api/run；本次修复已补齐该路由。
确定性组队DigitalTwin.form_team() 依据目标关键词选择候选员工，受最大并行人数策略限制；当前这个执行函数实际按顺序逐个运行。
↓
执行器模拟模式运行演示 worker；配置 LLM/搜索后由 Hybrid executor 按能力路由。这个路径不会调用 plan_project() 生成 LLM 任务计划。
↓
汇总与演示决策更新工作台状态、输出和证据列表。模拟模式可产生明确标记的 demo 决策；实时模型文字不会自动成为证据。

路径 B · 数字分身 ↔ 员工任务信箱

入口：POST /api/twin/goal、POST /api/twin/review、/api/workforce/*、/api/workers/heartbeat
分身接收目标并创建任务POST /api/twin/goal 默认单员工优先；只有显式选择 decompose 才拆分任务。
↓
员工领取 / 心跳检查 worker 身份、任务分配、租约和活跃状态；心跳不能代替任务结果。
↓
员工提交进度与结果状态机只允许特定活跃状态接收事件；验收中的任务不能再被迟到事件覆盖。
↓
分身读取员工反馈POST /api/twin/review 按任务状态给出继续观察、等待独立验收或需要重规划的决策；不自动重试、不自动验收。
↓
独立验收 / 重试管理员验收、证据字段、尝试上限和状态转换由代码执行。
↓
观察式改进报告GET /api/improvement/report只读；需管理员 Token，不会自动执行建议。
重要现状：这两条路径目前是同一仓库里的两套接口/执行流，还没有完全统一成一个端到端运行时。界面能显示的内容取决于对应路径是否写入同一套状态与事件数据。

数字分身 ↔ 数字员工：谁负责什么？

数字分身 · 目标负责人 / 协调者

  • 保存用户目标、约束、完成标准与授权范围。
  • 先判断一个员工能否完成；只有并行拆分确有收益时才组织多个员工。
  • 根据能力和权限分配任务，不强制固定岗位编制。
  • 持续接收员工进度、问题、阻塞、结果和证据。
  • 反馈后做出可追踪决策：澄清、重规划、合并、取消、有限重试或询问用户。
  • 不把员工自报完成视为验收通过。

数字员工 · 有边界的执行代理

  • 只领取服务端允许的能力范围内的任务。
  • 报告进度、输出、证据、假设、不确定性和阻塞原因。
  • 遇到缺少信息或权限时请求澄清，不自行扩大范围。
  • 结果先进入待验收状态，由授权验收流程决定是否接受。
  • 不能验收自己的结果、冒充其他员工或修改自身权限。
1. 分身理解目标记录约束、完成标准、风险和自主权限；规则先检查权限与审批要求。
↓
2. 单员工优先判断单代理是否足够；若需要拆分，说明并行协作的质量、速度或风险收益。
↓
3. 分配任务 → 员工执行任务应包含输入、预期输出、验收标准、证据要求和工具权限；员工持续反馈。
↓
4. 分身处理反馈根据任务记录决定澄清、调整、合并、取消、有限重试或请求用户决策，并记录原因。
↓
5. 独立验收 → 更新目标进展验收通过才更新已接受结果；失败则反馈并进入受限恢复流程。
当前实现边界：仓库已有 Twin policy / bounded project loop、持久化 worker mailbox、心跳租约、反馈和验收状态。但工作台执行流、自主项目循环和持久化员工邮箱尚未统一成一个运行时；分身基于反馈作出的所有决策也还没有统一成一套完整的决策记录 API。

LLM 在什么时机真正生效？

阶段触发条件LLM 做什么不会替代什么
规划 /api/autonomous请求未提供 tasks，且启动时成功配置 JARVIS_LLM_BASE_URL、JARVIS_LLM_API_KEY、JARVIS_LLM_MODEL。生成有界 JSON 任务列表；代码再校验 ID、标题、能力类型和任务数量。不负责权限认证或审批；无效/异常响应退回确定性计划。
普通员工执行非研究任务被路由到 LLM executor，且模型配置有效。根据目标和任务指令生成工作输出。不自动浏览网页、不证明事实、不把模型文字变成外部证据。
研究搜索研究任务执行时配置了 JARVIS_SEARCH_ENDPOINT。搜索由外部 provider 执行，不是 LLM 自己搜索。未配置搜索时研究任务应失败关闭；不能拿 LLM 编写的答案冒充搜索结果。
研究综合搜索结果通过质量门槛、至少有一条合格证据，并配置完整 LLM 环境变量。LLM 只综合已提供的合格来源材料，并被要求引用来源 ID。没有合格证据则跳过 LLM 综合，保留确定性综合状态。
失败重规划/api/autonomous 有可用 planner client，且任务失败需要重规划。可参与生成替代任务建议。仍受计划校验、迭代上限与审批规则约束。
任务状态、权限、心跳、租约、重试次数、验收门槛每次相关 API 请求或状态转换。不需要调用 LLM。这些是确定性代码规则，不交给模型自由决定。

规则的优先级与事实边界

确定性规则（每次执行都生效）

  • 身份与角色权限、任务状态转换、worker 能力与租约检查。
  • 审批要求、最大重试次数、任务迭代上限、允许的 capability 集合。
  • 研究来源的基本格式检查、URL 去重、质量门槛。
  • 模拟 / LLM / 搜索的来源标记；缺少必需工具时失败关闭。
  • 观察式改进只报告信号与实验建议，不自行采纳。

模型输出的边界

  • LLM 是可选的规划器或任务执行器，不是权限系统。
  • LLM 输出即使状态为 completed，也不代表独立验收或事实为真。
  • 搜索摘要也不自动等于已验证事实；质量门槛目前主要是机械筛选。
  • 递归自我改进当前是观察与建议阶段，不会自主改代码、改变规则或部署。

下一步需要验证 / 补齐

  1. 把路径 A 与路径 B 的任务、事件、验收状态统一到一个可追踪的运行时，避免两个界面展示不同数据源。
  2. 给每次 LLM 调用写入可审计 trace：阶段、模型名、输入摘要、输出摘要、耗时、失败原因和费用（不记录密钥）。
  3. 增强证据验证：检查来源可访问性、发布时间、来源独立性，以及结论是否真的被来源支持。
  4. 在安全隔离的测试环境中跑通完整闭环，再决定是否开放真实工具或更高自主权。
